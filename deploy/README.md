# Стенды

Три стенда на одной машине за одним входным nginx: `http://dev.ofera.localhost:8088`, `http://stage.ofera.localhost:8088`, `http://prod.ofera.localhost:8088`. Образ один, у стенда свой compose-проект, база и настройки. На dev и stage есть плашка и заголовок `X-Robots-Tag: noindex`, на проде их нет. Пульт `/__chaos` и `/__check` открыты только на dev.

**Какие браузеры откроют адрес.** Chrome и Firefox сами направляют `*.localhost` на эту машину. Safari и всё на системном WebKit адрес не находят: добавь строку в `/etc/hosts`:

```
127.0.0.1 dev.ofera.localhost stage.ofera.localhost prod.ofera.localhost
```

`curl` на macOS открывает эти адреса сам, а `ping` и `dscacheutil` — только после этой строки.

**Выкатка.** Тег образа лежит в `deploy/<стенд>.env`, одна строка `IMAGE_TAG=<sha>`. Для stage и prod файл пишет CI на ветку `deploy`, для dev его создаёшь сам. Агент запускается из `net-lab/` на сайте:

```bash
npm run ship:agent -- stage --watch
```

Он раз в 15 с смотрит тег, скачивает образы, поднимает стенд и ждёт health. Если новая версия не поднялась, он сам возвращает прежний тег, а в журнале пишет, почему.

## Выкатка без простоя

Если в корне проекта есть `compose.slot.yaml`, агент выкатывает по схеме blue-green. У стенда два слота, `ofera-stage-blue` и `ofera-stage-green`, том с базой у них общий: `ofera-stage_data`.

1. Новая версия поднимается в свободном слоте и проверяет себя на копии базы. Запросы к ней пока придерживаются.
2. Агент спрашивает `/api/version` у нового слота изнутри входа. Не ответила или ответила не та версия — слот останавливается, а люди ничего не заметили.
3. Вход переключается: `deploy/slots/stage.conf` и `nginx -s reload`. Начатые запросы дорабатывают по старому пути.
4. Старая версия дорабатывает начатое, пишет файл базы и выходит. Открытый поток SSE обрывается, браузер переподключается сам.
5. Новая версия получает `SIGUSR2`, читает файл и отвечает на придержанные запросы.

Шаги 4 и 5 нужны, потому что база живёт в памяти процесса `api`. Если новая версия прочитает файл раньше, записи последних секунд пропадут: это проверено контрольным прогоном. С отдельной базой такого шага нет, но обе версии будут работать с ней одновременно. Поэтому новые поля добавляют по схеме из [docs/expand-contract.md](../docs/expand-contract.md).

Какая версия ответила, видно на любом ответе: заголовок `X-Release` и адрес `/version`.

**Откат.** Из `net-lab/`:

```bash
npm run ship:rollback -- stage
```

Команда возвращает предыдущую версию из `deploy/slots/stage.history` тем же путём и записывает откаченный тег в `deploy/slots/stage.rejected`, иначе агент выкатил бы его снова. Этот тег больше не катится, пока в `deploy/stage.env` не появится другой. Чтобы выкатить его ещё раз, удали этот файл.

**Нагрузка на время выкатки.** Запусти в соседнем терминале, код выхода 0 значит ни одной ошибки:

```bash
npm run ship:load -- stage --sec 40
```

Считает ответы по статусам и версиям, поток SSE и записи: в конце база должна совпасть с последним подтверждённым ответом каждой.

**Что выкатка не сохраняет.** Счётчики лимитов и попыток входа и историю событий потока: они в памяти процесса. Событие, которое пришло во время переключения, поток не догонит. Если новая версия прошла проверки, а упала уже после передачи базы, люди увидят 502 на несколько секунд, пока агент возвращает прежнюю.
