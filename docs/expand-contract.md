# Новое поле при выкатке без простоя

Во время выкатки и после отката новая и старая версии работают с одними данными. Поэтому изменение идёт тремя релизами, и каждый из них можно откатить отдельно.

| Релиз | Что делает | Старая версия | Откат |
| --- | --- | --- | --- |
| Expand | Добавляет необязательное поле. Читает `displayName ?? login`, пишет только по явному запросу | Не знает о поле, строка при записи сохраняется целиком | Безопасен: поле просто лежит |
| Переход | Заполняет поле у всех строк, клиенты читают его | Всё ещё работает | Безопасен |
| Contract | Убирает запасной путь и старое поле. Выкатывается, только когда предыдущих версий нигде нет | Сломается | Назад только через новый релиз |

В этом проекте сделан первый шаг: `publicUser` в `api/auth.js`, адрес `PUT /me/display-name`, проверка в `api/expand.test.js`.

**Почему не одним релизом.** Если переименовать поле сразу, код нового релиза не найдёт его у старых строк, а после отката старый код не найдёт уже у новых. То же с открытыми вкладками: старый фронт ещё работает и ждёт старый формат ответа. Новое поле старому фронту не мешает, удалённое ломает.

**Где здесь другая цена.** База лежит в памяти процесса `api`, поэтому писатель один, а версии меняются передачей файла. В обычном проекте база отдельная, и обе версии пишут в неё одновременно: без схемы expand/contract там сломается уже сама выкатка.
