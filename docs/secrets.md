# Секреты

## Где что лежит

| Секрет | Где живёт | Кто видит |
| --- | --- | --- |
| Ключ JWT стенда | `secrets/<стенд>.jwt` на машине стенда, внутри контейнера `/run/secrets/jwt` | только `api` этого стенда |
| Токен реестра npm | окружение сборки, в `RUN` приходит через `--mount=type=secret` | один шаг сборки |

Каталог `secrets/` закрыт в `.gitignore`. Значения в `.env.example` и в коде не пишем, только имена.

```bash
npm run secrets:init                # ключи dev, stage, prod; существующие не трогает
npm run secrets:rotate -- prod      # новый ключ стенду
npm run secrets:scan                # вся история git
npm run secrets:hook                # включить pre-commit, один раз на клон
```

У каждого стенда свой ключ, поэтому токен со stage на проде получит 401. Стенд выбирает `OFERA_STAND`: без него берётся `dev`.

Без файла `api` в production не стартует, и это намеренно. Вне production, при `npm run dev`, ключ создаётся в `db.meta`, чтобы для разработки ничего настраивать не пришлось.

На Linux файл ключа попадает в контейнер с правами хозяина машины. Процесс `api` работает от uid 1000. Другой uid на машине даст `EACCES` при старте, тогда нужно `sudo chown 1000 secrets/*.jwt`.

## Токен в сборке

```bash
docker build --secret id=npm_token,env=NPM_TOKEN -t ofera-api api
```

`ARG` для этого не годится: значение остаётся в образе, и его покажет `docker history --no-trunc`. Секрет из `--mount=type=secret` есть только на время одного `RUN`.

Смена токена не пересобирает слой: кэш не зависит от значения секрета.

## Если ключ утёк

Порядок важен. Считай значение известным с момента пуша: публичные репозитории постоянно сканируют боты, а клоны и форки чистка не достанет.

1. **Ротация, сразу.** Старый ключ должен перестать работать раньше всего остального.

   ```bash
   npm run secrets:rotate -- prod
   OFERA_STAND=prod docker compose up -d --force-recreate api
   ```

   Токены на старом ключе, в том числе поддельные, сразу получают 401. Пользователи при этом не вылетают: refresh-токен не зависит от ключа JWT, и клиент получает новый access-токен сам.

2. **Журналы.** Что делали с этим ключом с момента утечки: необычные входы, запросы с чужих адресов, действия от имени администратора. Ключ JWT позволял подделать любого пользователя.

3. **Сканер.** Если его не было, включить, чтобы такой коммит больше не прошёл: `npm run secrets:hook` и workflow `Secrets`.

   ```bash
   npm run secrets:scan     # называет файл и коммит, значение скрыто
   ```

4. **Чистка истории.** Она убирает значение из веток, но не отменяет утечку, поэтому идёт последней. Хэши коммитов изменятся, так что сначала нужно предупредить тех, кто работает с веткой.

   ```bash
   git filter-repo --force --path .env.prod --invert-paths --refs leak/demo   # только эта ветка
   git fetch origin
   git push --force-with-lease origin leak/demo
   npm run secrets:scan
   ```

   `--force` нужен, потому что `filter-repo` работает только на свежем клоне, а тут есть другие ветки и remote. Вся история чистится именно на свежем клоне и без `--force` и `--refs`: `filter-repo` снимает `origin`, его нужно добавить заново и отправить все ветки и теги. Новый клон после этого чист, но остаётся то, что `filter-repo` не достанет:

   - клоны коллег: им нужно клонировать заново, иначе старые коммиты вернутся следующим пушем;
   - форки и ссылки PR на хостинге;
   - старые коммиты по прямому хэшу, пока хостинг их не удалит. Для этого пишут в поддержку хостинга.

5. **Разбор.** Как значение попало в коммит и какая проверка это остановит в следующий раз.
